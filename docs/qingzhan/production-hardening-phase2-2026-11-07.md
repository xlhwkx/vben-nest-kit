# 第二批生产加固：授权事务、审计与真实环境验证

> 后续输入校验与最新回归结果见[第三批加固记录](./production-hardening-phase3-2026-11-07.md)。本文保留第二批完成时的验证基线。

本批继续落实[企业级评估](./enterprise-readiness-review-2026-11-07.md)和[首批加固](./production-hardening-2026-11-07.md)中的高优先级问题。代码只修改在本地工作区；验证使用临时 PostgreSQL 16、Redis 7 和本地生产镜像，没有连接业务数据库，也没有提交、推送或部署线上服务。

## 授权修改的一致性

用户、角色、菜单管理的创建、修改、删除统一经过 `authorizationMutation`。事务先取得 PostgreSQL advisory transaction lock，再锁定操作者用户行，重新检查账号状态、tokenVersion 和本次操作所需的接口权限；授权边界检查、实际写入和成功审计都使用同一个事务客户端。等待期间被撤权的请求不能沿用 Guard 先前通过的结果。

采用 Read Committed，使取得锁之后的查询能看到上一个授权事务的提交。授权写入全局串行，适用于低频后台管理；它增加了事务查询和等待成本，不能当成高吞吐业务写入的通用模板。密码哈希在进入授权锁之前计算，缩短锁占用。

锁等待最多 5 秒；事务最大执行时间 20 秒、连接获取等待最多 10 秒。已识别的锁超时、死锁和 Prisma 事务资源超时返回可重试的 503。调用方应有限重试并重新拉取权限，不应连续无间隔重试。普通数据校验和权限拒绝仍保留原有错误语义。

事务提交前检查最后管理员：若修改前存在有效的完整系统管理员，修改后必须仍至少保留一名。完整管理员指未删除、启用的用户，通过启用角色和启用且未删除的菜单，合计持有 `SYSTEM_PERMISSION_CODES` 中全部 22 项系统权限；可以跨多个角色组合。删除用户、禁用角色、撤销菜单授权等操作均受此保护，违规返回 409 并回滚。历史数据库原本就没有完整管理员时，此规则不会凭空修复权限。

该一致性约束依赖所有授权写入遵循同一入口。直接 SQL、旧版本服务、外部同步脚本不会自动取得此锁；升级时仍应停止旧版本并审查自定义写入路径。未加入组织数据范围和租户隔离。

## 审计与停机

- 用户、角色、菜单管理的成功审计与修改处于同一事务，审计存储失败会导致修改回滚。
- 成功登录、刷新以及有效退出的审计与会话写入处于同一事务，提交成功后才设置响应 Cookie。
- 审计 detail 对对象和数组递归处理，移除 password、token、secret、cookie、credential、apiKey 等敏感字段，并限制遍历深度。
- 尽力写入的审计会跟踪待完成 Promise。停机先等待 HTTP 请求结束，再在剩余停机预算内等待这些写入，最后销毁 Prisma/Redis。

部门、字典、上传、被拒绝的认证等路径仍使用尽力写入审计。停机等待无法保障进程崩溃、断电或预算耗尽时的数据持久性；本批没有实现 outbox，也没有承诺外部副作用与数据库原子提交。

## 指标与异常定位

HTTP 统计从 interceptor 移到响应生命周期 middleware，覆盖在 Guard 阶段结束的 401、403、429、503，以及 404。`finish`/`close` 只记录一次；响应未完成即断连按 499 统计。抓取 metrics 自身不计入业务请求计数。

保留原有总量和延迟指标，增加 `qingzhan_http_responses_total{status="..."}`。服务端 5xx 输出含 requestId、方法、去掉查询串的路径、状态、异常类型和有限调用帧的 JSON 日志，不记录请求体、查询参数、凭证或异常消息。详见[可观测性说明](./observability.md)。

本批没有新增数据库迁移，首批 `20261107010000_authorization_and_sessions` 仍是升级必需项。CI 已配置相应检查，但本地通过不代表远端 CI 已执行。

## 对企业底座的判断与后续工作

授权并发、关键审计原子性和生产包可运行性已有代码和真实环境证据，作为内部管理系统二开基础的可信度得到提升。现有测试不能证明长时间运行、极限负载和任意二开代码的稳定性。

下一步仍应按实际业务补齐：组织/租户数据范围，剩余审计的可靠投递与外部副作用 outbox，输入与列表校验一致性，剩余依赖公告核查与前端生产裁剪，以及带目标容量的压测、备份恢复和故障演练。最后管理员保护与授权全局锁也应纳入这些容量和运维验证。
