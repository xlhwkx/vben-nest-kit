# 第六轮复核：仍未关闭的上传、积压与运维问题

本轮回答“还有什么问题”，执行定向复核和受控实验，没有修改业务实现，没有连接线上服务。前五轮通过的测试不代表下列问题已经解决。

后续状态：四项主要问题的修复、维护入口和验证结果已记录在[第七轮修复报告](./production-hardening-phase7-2026-11-07.md)。本文保留为修复前证据。

## 1. 上传没有限制 multipart 普通字段总量（高优先级）

`apps/server/src/modules/upload/upload.module.ts` 目前只配置 `limits: { fileSize, files: 1 }`。普通字段的数量和 multipart 总 part 数没有显式上限；每个字段虽有解析器默认大小限制，但多个字段的总量仍可继续累积。

使用实际编译后的 UploadModule 搭建本地隔离 HTTP 夹具，配置 `UPLOAD_MAX_BYTES=1024`，上传 16 字节的有效文本文件，另带 12 个各 512 KiB 的普通字段。返回 HTTP 200，解析后的普通字段合计 **6291456 字节**，存储调用成功一次。普通字段没有业务用途，但仍被解析并保留在请求体中。

这是组件 HTTP 实验，夹具省略了全局认证，不能据此声称匿名可上传；真实 AppModule 的 JWT Guard 在上传拦截器之前执行。已登录调用仍可触发该资源路径。没有进行耗尽内存或生产压测。

建议：按现有“仅 file 文件”契约限制普通字段数量、字段大小和 part 总数，并配置上传并发/超时及入口总请求大小。允许扩展元数据时应显式定义少量字段和总预算。仅增加 UPLOAD_MAX_BYTES 不能解决额外字段积累，也不能替代并发预算。

## 2. 尽力审计没有积压上限（高优先级，故障放大路径）

`AuditService.record()` 每次立即发起写入，并把 Promise 放入 pending Set；没有待完成数量上限、并发上限或降载机制。事务内成功审计使用另一条路径，本项针对登录失败/锁定、上传等尽力写入。

用不会完成的审计数据库写入替身模拟阻塞，连续调用 1000 次 record，pending 实际达到 **1000**。这证明应用层没有该边界，不代表已证明生产数据库必然永久阻塞或 1000 条记录就会耗尽内存。实际影响取决于数据库/连接池等待时间、流量、进程预算和限流故障策略；当前代码没有为这一队列给出明确上界。

建议：为尽力审计配置有限并发与积压预算，溢出必须可观测；需要可靠投递的事件走事务内审计/outbox，不能把静默丢弃当作可靠审计。还应配置数据库连接/语句超时并覆盖恢复测试。直接给 Promise 增加超时但不取消底层查询，不能真正限制数据库侧积压。

## 3. S3 与上传参数仍未进入生产 Compose（中优先级，已知未关闭项）

第五轮补齐了认证配置映射，但 `compose.prod.yml` 仍只传 STORAGE_DRIVER 和固定 UPLOAD_DIR，没有 S3 凭据/endpoint/bucket，也未传 UPLOAD_MAX_BYTES 等参数。

本轮用仅用于渲染的虚拟配置设置 STORAGE_DRIVER=s3、S3_BUCKET、S3_ACCESS_KEY_ID、S3_SECRET_ACCESS_KEY、S3_ENDPOINT 和 UPLOAD_MAX_BYTES=1024，再执行 `docker compose config --format json`。结果 STORAGE_DRIVER 为 s3，但上述其余五个键均不存在于 server.environment。S3StorageProvider 初始化要求 bucket 和凭据，因此按此模板切换 S3 会缺配置，上传大小也继续采用服务端默认值。

这是配置渲染与初始化代码证据，没有连接或验证真实 S3。最初评估报告已经记录过该项，此处不作为新发现重复计数。需要补齐生产模板映射和对象存储上传/读取验证，不能把任意 env-file 键当成自动进入容器。

## 4. 会话与审计缺少已落地的生命周期清理（中优先级，已知未关闭项）

认证登录和每次 refresh 都插入 RefreshToken；已消费记录标记 revokedAt，但运行路径中未见按到期清理的实现。AuditLog 也没有已落地的归档/保留任务。expiresAt 索引已经存在，索引本身不会删除记录。

这是源码复核，没有生产数据增长曲线。长期运行会持续积累历史会话和审计；影响应通过实际刷新频率、保留期和查询计划评估。清理策略必须保留有效会话及注销所依赖的 family 语义；审计保留期也不能未经业务约定随意设定。建议提供有批次上限、可预览和可观测的维护入口，再进行恢复验证。

## 5. 可选骨架能力仍需按真实状态评估

SMTP provider 仍明确是 dry-run/no-op。本轮把目标设为 127.0.0.1:1 后调用 send，仍成功完成；源码没有打开 SMTP 连接。队列审计归档 worker 也仍是 stub，不执行实际归档。

这些能力在代码和原评估中已有说明，不应当作新的安全漏洞。但企业二开如果准备依赖邮件通知、找回密码或自动审计归档，就不能把配置 driver=smtp、入队成功或任务完成当作外部业务已经送达。

## 证据与范围

受控脚本及 phase6-probe-results.json、phase6-compose-results.json 保存在仓库外的本机企业评估产物目录。本轮没有新增容器，也没有停止用户已有服务。没有修改业务代码，未重跑与这些未修改实现无关的全套回归；前五轮验证记录仍以对应报告为准。

这些项目之外，单租户之外的数据隔离、私有文件授权及长时间/多实例容量验证仍按第五轮报告列出的边界处理。本轮应优先关闭上传总量与审计积压，再处理部署模板和生命周期维护。
