## 结论

仍发现 1 项应优先修复的 P1，以及 3 项 P2。最需要优先修复的是后端菜单配置直接进入无隔离 iframe 的存储型 XSS 风险链路。跨标签页的账号一致性也是认证链路的剩余缺口。

当前工程已有二开底座的主要结构，但在修复这些问题并完成对应验证前，不宜直接认定为已经满足企业生产要求。源码审查能够确认缺少哪些约束，不能证明浏览器实际行为、并发容量、恢复能力或长期稳定性。

## S11-01：菜单配置可以进入脚本执行上下文

源码链路：

1. `apps/server/src/modules/system/menu/system-menu.controller.ts:39`：`meta` 只约束 `order`，其余字段经 `catchall(z.unknown())` 接受，未校验 `iframeSrc` 的类型、协议或来源。
2. `apps/server/src/modules/system/menu/system-menu.service.ts:184`、`:263`：创建和更新把 meta 写入 JSON；菜单编辑权限和版本检查不能替代内容校验。
3. `apps/server/src/modules/menu/menu.service.ts:90`：菜单接口将数据库 meta 原样输出。
4. `packages/utils/src/helpers/generate-routes-backend.ts:62`：路由转换保留 meta，没有对 URL 做安全过滤。
5. `packages/effects/layouts/src/iframe/iframe-router-view.vue:79`：`item.meta.iframeSrc` 直接绑定 iframe 的 src，没有协议过滤，也没有 sandbox。第 22、24 行按 iframeSrc 是否存在选择渲染对象，而非按服务端菜单类型建立安全约束。

例如，直接提交带 `javascript:` 协议的 iframeSrc 可以通过当前后端 schema。前端表单即使限制 URL，也不能阻止直接 API 提交，更不能保护已有数据库中的危险配置。

影响与边界：

- 初始 iframe 继承父页面来源的情况下，脚本 URL 会形成访问父页面的风险；能否实际执行还受浏览器和部署 CSP 等条件影响，本轮未进行浏览器复现。
- 若脚本获得父页面的同源执行能力，就能读取前端可访问的状态，或代表当前登录用户发起认证请求。HttpOnly 仅限制直接读取刷新 Cookie，不能消除同源脚本代用户操作的风险。
- 需要攻击者拥有相应菜单编辑能力，并让受害者访问该菜单。这不是匿名攻击入口，也不是服务端代码执行。
- 委派权限检查主要约束 authCode。`permission-codes.ts:44` 只收集非空 authCode，编辑共享的无权限码页面不能据此视为无害。攻击者不必直接拥有受害者的全部 API 权限。

建议修复：

- 服务端对已知 meta 字段建立明确 schema，URL 使用解析后的 HTTP(S) 协议白名单，按业务决定允许的来源；同时校验 embedded/link 类型与相关字段的组合。
- 前端在实际 iframe 渲染点再次拒绝危险 URL，覆盖旧数据、其他菜单来源和未来接口遗漏。
- iframe 根据功能配置最小 sandbox 权限；同源且允许脚本时，不要把 `allow-scripts` 与 `allow-same-origin` 的组合当作可靠隔离。不可信内容需要独立来源。
- 检查历史菜单及缓存标签页中的 iframeSrc，修复后不能只限制新增记录。

修复后需要验证：混合大小写及控制字符等 URL 变体、危险协议、历史菜单、不同标签页显示模式，以及允许的正常嵌入页面。这些是后续验收项，本轮未执行。

## S11-02：刷新成功不等于仍是原账号

源码链路：

- `apps/server/src/modules/auth/auth.service.ts:57`、`:299`：登录使用同一个名为 jwt、path=/ 的 HttpOnly Cookie。相同 Cookie 范围内，另一个标签页登录会替换它。
- 同文件 `:315`、`:373`：刷新根据当前 Cookie 确定用户，返回新的 access token，不校验它是否属于发起原请求的账号。
- `apps/web-antd/src/api/request.ts:53` 和 `playground/src/api/request.ts:67`：刷新后只调用 setAccessToken，没有检查用户身份或重建用户信息、权限码和动态路由。
- `packages/effects/request/src/request-client/preset-interceptors.ts:96`：刷新成功后自动重放原请求；排队请求也会重放，未限制为只读方法。
- `packages/effects/request/src/request-client/refresh-coordinator.ts:13`：锁按 API origin 协调刷新，没有将登录、退出和账号世代纳入协调。
- `packages/stores/src/modules/access.ts:85`：setAccessToken 只更新 token。`apps/web-antd/src/router/guard.ts:89` 在 isAccessChecked 为真时跳过路由重建。存储持久化本身不等于同步另一个标签页已经加载的内存状态。

具体条件：标签页 A 仍显示账号 A；标签页 B 登录账号 B，替换共享 Cookie；A 的请求遇到 401，刷新得到 B 的 token，然后自动重放 A 原本的操作。此时服务端会按 B 正常鉴权，但 A 页面仍可能显示 A 的用户信息和上下文。

风险是错误账号下的操作、审计归属和界面身份混淆。服务端不会因此接受 B 无权执行的动作；有编辑版本检查的接口也可能拒绝部分旧写入，不能据此声称任意写入必然成功。该问题也不要求跨域 Cookie 泄露。

建议修复：

- 在请求开始时保留预期用户和会话世代，将刷新结果与其核对；身份变化时拒绝原请求及等待队列的自动重放。
- 刷新接口应能提供可核对的用户标识。后端可进一步将刷新绑定到预期身份，避免客户端无意接受另一个账号的续期结果。
- 登录、退出、账号切换通过跨标签页通知更新世代并使旧上下文失效；通知不需要广播 token。
- 身份变化后清理用户、权限、路由及业务表单上下文，要求用户重新确认操作。仅刷新头像或放宽 Web Lock 不能解决旧请求重放。

后续验证应覆盖双账号双标签页、排队写请求、登录与刷新竞争、退出与刷新竞争。此前同账号双标签页续期通过，不代表此场景已覆盖。

## S11-03：服务端退出失败被伪装成本地正常退出

`apps/web-antd/src/store/auth.ts:110` 和 `playground/src/store/auth.ts:90` 在显式退出时调用 logoutApi，但 catch 不做处理，随后清空 store 并跳回登录页。logoutApi 使用 baseRequestClient，没有接入普通 requestClient 的统一错误提示。

`apps/server/src/modules/auth/auth.service.ts:395` 的撤销事务失败会向外抛错，`:428` 的 clearRefreshCookie 在事务之后。因此网络失败或事务失败时，界面虽然退出，服务端 refresh family 及 HttpOnly Cookie 仍可能有效。

这与“成功退出后，已有 access token 按既定策略保持到过期”不同：本问题发生在刷新会话撤销没有成功的情况下。当前登录页本身不会因此自动恢复登录，不能把会话仍有效描述成必然立即回到原账号。

建议显式区分“本地已退出”和“服务端撤销未完成”，展示失败并提供重试；在未完成撤销期间阻止旧请求或延迟刷新结果重新写入认证状态。保留被动重新认证的 revokeSession:false 语义，避免旧标签页的失败误撤销其他标签页会话。

## S11-04：readiness 的公开访问绕过业务限流

`apps/server/src/modules/health/health.controller.ts:19`、`:20` 的类级 Public/SkipThrottle 同时作用于 ready。`health.service.ts:30` 每次 ready 都执行 SELECT 1 和 redis.ping，没有短时状态缓存、请求合并或独立并发约束。

当反向代理转发整个 /api 路径并暴露 ready 时，匿名请求可以绕过正常业务限流，持续向同一业务数据库连接池及 Redis 提交探测。依赖已经变慢时，这会增加资源竞争。

现有 Prisma 池大小、连接超时和语句超时仍然有效（`prisma.service.ts:12`）；这里没有认定存在无限数据库连接，也没有通过压测证明服务会被打垮。若 ingress 已将探针限制为内部访问，实际风险会明显降低。

建议将依赖探针限制为内部入口；需要公开时，为 ready 设置独立限流、短时缓存和并发请求合并。无依赖的 live 可继续保持低成本，并避免将缓存后的业务状态误用为进程存活状态。
