# 第四轮深挖：部门并发、字典失效与一次性票据

本轮不是仅凭代码猜测问题。先在隔离的 PostgreSQL 16 / Redis 7 中运行第三批编译产物，通过控制实际查询的交错验证缺陷，再修复并加入回归。所有修改仍在本地工作区，没有提交、推送或部署线上服务。

## 已确认并修复的问题

| 问题与影响 | 修复与验证 |
| --- | --- |
| 两个管理员同时把部门 A 移到 B 下、把 B 移到 A 下，各自的后代检查都可能通过。实验中两个更新均成功，数据库出现环，树列表可能漏掉这些节点 | 部门写入接入与用户管理相同的管理事务锁。第二个写入等待后重新检查后代关系；真实数据库回归验证第二次移动拒绝，未产生环 |
| 删除部门检查到“没有用户”后，另一个请求仍可分配用户到该部门；软删除不会触发外键约束。实验中用户最终引用已删除部门 | 用户分配与部门创建/移动/删除共享同一个锁和事务协议。覆盖删除先提交、分配先提交两种交错，分别拒绝失效分配或拒绝删除 |
| 字典类型已禁用，但 `/dict/data?code=...` 只过滤条目状态。实验仍返回 1 个启用条目，与 `/dict/all` 不一致 | 按编码查询同时过滤类型与条目状态；禁用类型不返回条目，重新启用后恢复 |
| 字典先提交数据库，再尽力更新 Redis 版本。实验断开 Redis 后修改成功，重连后版本仍为原值，客户端可能长期保留旧缓存 | 新增 PostgreSQL `dictionary_revision` 单例表及两个字典表的触发器，版本与数据在同一事务提交/回滚。版本接口直接读 PostgreSQL，不再依赖 Redis 计数器 |
| 一次性验证码使用分开的 GET/DEL。实验让两个 GET 都先完成，同一票据两次验证均通过 | 改为 Redis GETDEL 原子消费；票据写入也使用传播错误的接口。Redis 故障返回 503，过期、错误或已消费票据返回 400 |

部门、字典的创建、更新、删除同时补上事务内的操作者状态/权限复核与成功审计。等待期间被撤权的请求拒绝执行；审计失败则数据、审计与字典版本共同回滚。用户/角色/菜单/部门/字典这五类管理写入现在遵循同一管理锁协议。

字典全量拉取还改为固定两次查询，在 Repeatable Read 快照中组装结果，替代按类型逐个查询的 N+1 路径。用 Map 与 `Object.fromEntries` 组装返回对象，服务端不再因 `__proto__` 等特殊编码丢失字典键；新增了真实 HTTP JSON 返回回归。这不代表所有前端扩展代码都天然安全地处理特殊对象属性名。

## 迁移、兼容性与成本

必须先备份数据库并应用 **`20261107020000_dictionary_revision`**，再启动本轮代码。现有七个迁移之后增加第八个迁移，不改写历史迁移文件。升级应停止旧版写服务，避免没有遵循部门互斥协议的旧代码继续运行。

- 新增单例版本以迁移执行时的毫秒时间初始化，让旧 Redis 版本缓存发生失效。API 仍返回 JavaScript 安全整数 number；版本无需连续，也不等同于修改次数。
- 类型/条目的 INSERT、UPDATE、DELETE、TRUNCATE 触发版本变化，包括种子、导入脚本、外键级联等直接数据库写入。触发器与数据同事务；事务失败不会提前发布版本。未匹配行的语句或级联可能产生额外版本变化，这是允许的缓存刷新。
- `version` 在数据库内部使用 bigint，并通过 CHECK 约束保持在 1 至 `Number.MAX_SAFE_INTEGER` 之间。版本状态缺失时，触发器使写入失败，避免静默丢失失效通知。
- Redis 原有 `qingzhan:dict:version` 键不再使用，无需在线手动删除。PostgreSQL 不可用时版本接口会报错，不返回伪造的固定版本或时间戳。
- 字典选项是可登录用户读取的公共配置；类型禁用是可用性规则，不替代业务机密数据授权。
- 验证码要求 Redis >= 6.2，项目验证目标仍是 Redis 7。对外路径和票据字段保持不变，存储不可用从 400 调整为 503。
- 部门/字典写服务增加显式 `AuthUser` 参数；自定义内部调用也必须传入操作者。绕过服务直接写部门/用户引用的脚本必须遵循同一 advisory lock 协议。

管理写入全局串行、审计写入失败会阻止业务提交，都是明确取舍：适用于低频管理操作，增加了数据库查询、锁等待和对审计存储的依赖。锁等待仍为 5 秒，资源超时返回 503。不能把这一做法复制为所有高频业务写入的通用方案。

## 仍存在的边界

1. **验证码票据不等于服务端人机验证。** `/auth/captcha` 公开返回票据，自动程序也可获取；前端滑块不能独立证明真人。本轮修复了一次性语义，但没有引入真正的服务端人机挑战或风险引擎。依赖这项能力防自动化攻击的部署仍需接入相应机制。
2. **历史异常部门数据不会自动修复。** 新协议阻止遵循协议的运行时写入制造环或失效引用；升级前已有的环、软删除引用，以及直接 SQL/旧版本写入，仍需核查和定向修复。树深度、最大节点规模和恢复流程尚无容量保证。
3. **组织数据范围、租户隔离和私有文件授权仍未实现。** 启用/禁用与管理接口权限不等价于按业务划分数据访问范围。
4. **审计可靠性仍有范围。** 五类管理修改和有效认证会话的成功审计已事务化；上传、拒绝认证等尽力写入路径与外部存储副作用仍没有 outbox。后台审计 drain 无法覆盖断电或进程崩溃。
5. **依赖与故障策略还要专项检查。** 仍未完成全部依赖公告清理、长时间压测、多实例/网络分区演练和跨站 Cookie 的专项安全验收。登录失败计数的 INCR/TTL 仍是多条 Redis 命令，其故障交错需要后续回归。
6. **恢复证据来自小型隔离库。** 本轮验证了结构、数据库内容与触发器恢复，没有恢复上传目录/对象存储、验证完整业务流，也不能推导生产 RPO/RTO 或 SLA。

以上结果继续提高了单租户内部管理底座的可靠性证据，但不足以承诺任意二开场景下的企业级稳定性。
